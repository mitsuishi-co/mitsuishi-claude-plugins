# 社内標準 開発ワークフロー（プランナー／実行役 × gstack × Superpowers）

## 役割とモデル

| 役割 | 誰が | モデル | やること |
|---|---|---|---|
| プランナー | メインのセッション | Fable | 要件の整理、設計判断、計画書の作成、実行役への指示、結果の確認 |
| 実行役 | サブエージェント | Opus / Sonnet / Haiku | コードの実装、テスト、修正 |

- **プランナーはコードを直接編集しない。** コードの変更は、規模にかかわらず実行役のサブエージェントに委任する。プランナーが編集してよいのは計画書・設計書などの文書（`*.md`、`VERSION`、`CHANGELOG` など）だけ。これはフックで強制されている。
- **Fable はプランナー専用。** サブエージェントを起動するときに Fable を指定しない（フックで強制されている）。モデルは Superpowers の基準どおり、単純な実装は haiku、複数ファイルにまたがる実装やデバッグは sonnet、難しい判断を伴う実装やレビューは opus を指定する。指定しない場合は既定の実行役モデルになる。

## 工程と分担

| 工程 | 担当 | 使うもの |
|---|---|---|
| 1. 企画・設計判断 | プランナー（gstack） | `/office-hours`、`/plan-ceo-review`、`/plan-eng-review`（UIがあれば `/plan-design-review`） |
| 2. 実装計画 | プランナー（Superpowers） | `writing-plans` |
| 3. 実装 | 実行役（Superpowers） | `subagent-driven-development`、TDD |
| 4. 最終確認・出荷 | プランナー（gstack） | `/review`、`/qa-only`、`/ship` |

## 重複と取り違えを避けるルール

- 工程1で gstack のレビューを通った設計がある場合、Superpowers の `brainstorming` は省略し、`writing-plans` から開始する。その設計内容を `writing-plans` の入力として渡す。
- 承認済みの設計がない状態でコードを書く依頼が来たら、まず工程1に戻る。いきなり実装しない。
- 工程3は必ず `subagent-driven-development` で行う。`executing-plans` はメインのセッションで実装してしまうため使わない。
- 工程3の各タスク後のレビュー（Superpowers の2段階レビュー）は省略しない。工程4の `/review` は、ブランチ全体を通した最終確認として別に行う。
- 工程4で問題が見つかった場合、プランナーは修正内容を指示書にまとめ、実行役のサブエージェントに修正させる。gstack の `/qa`（自分で修正するもの）ではなく、報告のみの `/qa-only` を使う。
- 不具合調査は Superpowers の `systematic-debugging` を使う。調査はプランナーが行ってよいが、修正は実行役に任せる。
- Web ブラウジングが必要なときは gstack の `/browse` を使う。

## 軽微な修正の扱い

誤字修正、設定値の変更、1ファイル内で完結する数行の修正など、設計判断を伴わない作業は工程1・2を省略してよい。
その場合も修正自体は実行役のサブエージェントに任せ、工程4の `/review` は行う。
省略してよいか迷う場合は、省略せずにユーザーに確認する。

## gstack の更新

gstack はセッション開始時に自動で最新版へ更新される（このプラグインのフックが実行する）。
セッション開始時に「gstack の更新に失敗した」「gstack が未インストール」などの通知があった場合は、gstack のコマンドを使う前にその内容をユーザーに伝え、指示を仰ぐ。
